# Architecture

IRHIS has three parts: a mobile app that patients and clinicians use, five Movella DOT inertial sensors worn on the legs and pelvis, and a backend API that stores users, sessions and metrics.

```
 Movella DOT x5 ──BLE──▶ Mobile app (React Native / Expo) ──HTTPS + JWT──▶ Flask API (Azure App Service) ──▶ MySQL (Azure)
                          • sensor connection                               • auth, patients, sessions
                          • recording                                        • metrics, feedback
                          • on-device analysis
```

Movement analysis runs **on the phone**. Raw sensor data never leaves the device; only the computed metrics (range of motion, velocities, repetitions, centre-of-mass excursion) are sent to the backend.

## Mobile app

### Navigation

The navigator switches on the logged-in user's role.

| Role | Bottom tabs |
|---|---|
| Patient | My Exercises · History · Sensors · Live Session |
| Doctor | Patients · Sensors · Live Session |

Stack screens open on top of the tabs: patient details, session details, exercise recording (`BleConnection`), sensor setup (`SensorSetup`, the same screen as the Sensors tab), profile, onboarding and account screens.

### State (React Context)

| Context | Responsibility |
|---|---|
| `AuthContext` | Login, logout, current user and JWT (kept in memory only, so users sign in again after the app restarts) |
| `PatientContext` | Patient lists, assigned exercises, sessions, doctor dashboard data |
| `HealthContext` / `HealthGoalsContext` | Step count and activity goals from the phone's pedometer |
| `SensorContext` | Movella DOT discovery, connection, body-position tags, readiness, recording lock |

### Sensor connection is independent of exercises

Sensors are managed in the **Sensors** tab through `SensorContext`, not inside the exercise flow:

1. `movellaBleService.ts` is a single shared service wrapping `react-native-ble-plx`. Several parts of the app can listen to its events at the same time through `addListener()`.
2. `SensorContext` listens for discovery, connection, disconnection, battery and error events, and exposes the sensor list and actions (scan, connect, disconnect, assign tag).
3. It also computes **readiness**: the app is ready to record when connected sensors cover all five body positions.
4. The recording screen only reads readiness and listens for measurement data. While a recording is running it sets a lock, and the Sensors tab blocks disconnects, rescans and tag changes.

`SensorContext` is where automatic reconnection and registration of known sensors will be added.

### Recording and analysis flow

```
Live Session tab
  └─ choose patient (doctor) and exercise
      └─ BLE Stream → Record Exercise screen
           ├─ sensors not ready → Manage Sensors (opens Sensors screen on top)
           ├─ Start Exercise  → startMeasurement on each sensor (Extended Quaternion payload)
           ├─ samples buffered per sensor in memory
           ├─ Stop Exercise   → stopMeasurement on each sensor
           └─ Analyze Exercise
                ├─ build a Session (quaternions + timestamps per body position)
                ├─ createLocalAnalysisApi().analyzeSession()   ← runs on the phone
                └─ createSessionFromAnalysisResult()           ← POSTs session + metrics to the API
```

See [analysis-pipeline.md](analysis-pipeline.md) for the maths and [sensors.md](sensors.md) for placement and data formats.

### Backend URL

`frontend/config/env.ts` uses `EXPO_PUBLIC_API_URL` if it is set, otherwise the production Azure URL. There is no automatic emulator detection, so set the variable when you develop against a local backend (see [development.md](development.md)).

## Backend

- **Flask 3** app in a single module (`app.py`), served by Gunicorn on Azure App Service (Python 3.11).
- **MySQL** on Azure, reached through SQLAlchemy Core with raw SQL in `db.py`. The connection comes from `DATABASE_URL`; without it the database is disabled and most endpoints return `500 Database not configured`.
- **Auth**: JWT (HS256) signed with `SECRET_KEY`, sent as `Authorization: Bearer <token>`. `/login` is rate-limited to 10 requests per minute per IP (in-memory limiter, so the limit is per instance).
- **Clinical-study logins**: during the clinical trial, patients and clinicians sign in with generated access codes (`IRHIS-XXXXXX` for patients, `IRHIS-D-XXXXXX` for clinicians) instead of email. These are stored in the existing `users` table as a temporary compatibility layer (see `db.py`).
- **Access control**: patients can only reach their own data; doctors only patients linked to them in `patientdoctor`. See [api.md](api.md#access-rules).
- **Accounts**: public sign-up is switched off (the screen is hidden and `/signup` returns 404 unless `PUBLIC_SIGNUP_ENABLED=true`). Doctors create patients in the app (which links them automatically); doctor accounts are created by an administrator with `backend/create_doctor.py`.

Endpoint reference: [api.md](api.md).

## Data stored in the backend

| Table | Contents |
|---|---|
| `users` | Accounts, role (Patient/Doctor), password hash |
| `patient` | Patient details and recovery process |
| `patientdoctor` | Doctor ↔ patient links |
| `session` | Assigned and completed exercise sessions |
| `metrics` | Per-session, per-joint ROM, velocities, repetitions, centre-of-mass displacement |
| `PatientFeedback` | Patient-reported pain, fatigue, difficulty and comments per session |

`metrics` and `PatientFeedback` have creation scripts in `backend/migrations/`. The other tables pre-date the migrations folder and have no creation scripts in the repository.
